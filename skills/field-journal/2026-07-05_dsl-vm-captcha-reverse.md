# Captcha System Complete Reverse Engineering Analysis

## Scenario
Target: Reverse engineering a major captcha system to understand its full operating principles and verification workflow.

## Target Entities
- **nc.js** (72KB) — Webpack-bundled slider core (9 modules)
- **fireyejs.js** (583KB) — DSL VM interpreter (26 opcode custom instruction set)
- **awsc.js** (9KB) — Module loader
- **secaptcha.js** (72KB) — WASM C compilation artifact (emscripten)
- **et_f.js** (262KB) — Another DSL VM file type

## Verified Technical Approaches

### Approach A: Selenium + CDP Drag-and-Drop (Recommended)
Send native mouse events via CDP `Input.dispatchMouseEvent` to complete verification inside a real browser.
- Success Rate: High
- Dependencies: Chrome + Selenium / Playwright

### Approach B: Playwright Headless Browser Runner
Load DSL VM and module loader inside Playwright, exposing tokens via HTTP API.
- Success Rate: Medium (Dependent on WASM initialization environment)

### Approach C: Pure Requests Protocol Verification
Directly invoke API endpoints via HTTP requests for verification.
- Success Rate: **Extremely Low** (Tokens are tightly bound to browser TLS/IP/fingerprints)
- Not recommended for use

## Critical Findings

1. **Tokens Cannot Be Used Outside Browser** — Tokens generated by the DSL VM are verified server-side for context consistency upon submission (TLS JA3, IP, Cookies, Referer, etc.)

2. **fireyejs.js Is a DSL VM, Not WASM Binary** — A 583KB custom virtual machine implemented in pure JS, executing encoded instructions via a 26-opcode interpreter loop

3. **nc.js 9 Modules 100% Reverse Engineered** — Covering API endpoints, slider UI, interaction logic, ncSessionID algorithm, i18n, etc.

4. **Real WASM Compilation Artifact Is secaptcha.js** — 72KB, utilizing SharedArrayBuffer + Atomics, compiled from C code via emscripten

## Lessons Learned & Pitfalls

1. Testing appkeys do not trigger real verification; must use appkeys from real production pages
2. `initialize` returning specific status codes indicates slider mode; returning `success` is merely session creation confirmation
3. JSONP request URL events in performance logs may be incompletely captured due to script tag injection methods
4. Exported function names do not exist in the DSL VM file (encoded by the VM); real exports are exposed via a module registry

## Reusable Patterns

- **DSL VM Reverse Engineering Pattern**: `Case Extraction → Opcode Classification → Constant Table Analysis → Function Tracing → Export Extraction`
- **Generic Captcha System Architecture**: `Entrypoint JS → Module Loader (WASM/DSL) → API Communication Layer → Frontend UI → Server Verification`
- **CDP Native Event Bypass**: `Input.dispatchMouseEvent` bypasses detection, independent of WebDriver

## Toolchain

- Selenium + CDP: Browser automation + native mouse events
- Playwright: Headless browser + route interception
- Python requests: Pure API calls (verification failed)
- Node.js + Playwright: Runner service
